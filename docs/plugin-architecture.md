# Plugin architecture

Status: built: steps 1–3 below are done; wave 3 builds on it. Replaces the ad hoc `CoreHost` / `MainHost` / `RendererPluginEntry` shapes that waves 1–2 grew one conversion at a time.

## 1. Goals

1. A plugin is a set of **interface implementations**. Implementing an extension point is the only way to appear in the app, and it is sufficient: the plugin then shows in Settings → Plugins and its contributions show in their slots.
2. **One model in every process.** Core, main and renderer share the same declarations, placement and messaging rules.
3. **A first-party boundary.** Bundled plugins import only the descriptor SDK (`@plugin-sdk/{shared,core,main,renderer}`, compile-time aliases built with the app), their own folder, and third-party packages; host internals are unreachable (test). Bundled plugins change with the SDK; installed plugins (§16) are built against a `PLUGIN_SDK_VERSION`, so the SDK is versioned too. Folder plugins' `PluginApi` (docs/plugins.md) is versioned separately.
4. **Declared before run.** Anything the host shows or routes without running plugin code (panels, settings pages, rule actions, Jev queries, channels, placement, data it adopts) is declared in the plugin's descriptor. The type system then requires each process to implement exactly what was declared.
5. **Stable naming.** Extension points are named after the host concept they extend (`derivedText`, `attachmentNotes`), never after the first plugin that needed them. A point is added to this catalog, with its contract, before code uses it.

## 2. Anatomy

```
plugins/<id>/           in a plugin repo; the app holds none
  shared/index.ts     default export: definePlugin({...})              declarations and the channel contract
  core/index.ts       default export: defineCorePlugin(plugin, activate)
  main/index.ts       default export: defineMainPlugin(plugin, activate)
  renderer/index.tsx  default export: defineRendererPlugin(plugin, contributions)
  page/index.html     optional: a page of its own, built as <id>.html (page/public/ copied to the output root)
```

Each side is optional except `shared`. In development the registry (`virtual:bundled-plugins/<process>`) compiles in the plugin folders `CHATTYPOP_PLUGIN_DIRS` names, chosen by `CHATTYPOP_PLUGINS`. Only the dev server reads them: a build (`build`, `dist`, `package`, `preview`) and the host's tests have none, and load installed plugins (§16).

```ts
// shared/index.ts
export const plugin = definePlugin({
  manifest: { id: 'transcription', name: 'Transcription', version: '1.0.0', description: '…' },
  channels: defineChannels<{ core: TranscriptionCore; events: TranscriptionEvents }>()({
    core: { status: { audiences: ['renderer', 'phone'], writes: false }, install: ['renderer'], request: ['renderer'], audioFetched: ['main'] },
    events: { status: ['renderer', 'phone'], fetchAudio: ['main'] },
  }),
  settings: [{ id: 'transcription', label: 'Transcription', tab: { after: 'archive', iconPath: '…' } }],
  preferences: { settings: definePreference({ default: DEFAULT_TRANSCRIPTION_SETTINGS, normalize: normalizeTranscriptionSettings }) },
  adopts: { tables: { transcripts: 'jobs' }, settings: { transcription: 'settings' }, dataDir: 'transcription' },
});
export default plugin;
```

`definePlugin` keeps literal ids (a `const` type parameter), so the other sides are typed from them:

| Declared | Core must | Renderer must |
|---|---|---|
| `panels[].id` | — | give `panels[id].view` |
| `settings[].id` | — | give `settings[id].body` |
| `slots.<slot>[].id` (§6) | — | give `<slot>[id]`, its view |
| `rules.{triggers, match, filters, actions}[].type` | register through the corresponding `ctx.rules` member | give `rules[section][type]` (editor, summary; filters also chips) |
| `channels.core` | `ctx.channels.serve({...})` with exactly those members | — |
| `channels.main` | — | — (main serves them) |
| `preferences` | `ctx.preferences.get/set/onChange` typed by name and value (main alike, asynchronously) | `pluginPreference(plugin, name)` typed by name and value |
| `jev.features[].key` | `ctx.jev.decider/isOn(key)`, per-message and rule-match questions' `feature(s)` name only these or host switches | give `jevFeatures[key]` (its Settings row); `jevSwitch(plugin, key)` (kit) reads and sets it |
| `notices[].kind` | — (main: `ctx.notifications.show({ kind })` names only these) | give `notificationKinds[kind]` (its phone choice) |
| `search.ranker: true` | `ctx.search.rerank(fn)`, once | — |

Core and main have an `activate(ctx)` that runs once and registers through `ctx`. It is synchronous in core, so bundled plugins register before the startup Jev catch-up. After any bundled activation (startup, or turning a plugin back on) the host requests one coalesced Jev catch-up, once the plugin's questions are registered and rules recompiled, so what arrived while it was off is judged. `ctx.session.resumed` tells an activation whether it continues the previous one without a gap (on through the end of the previous core session and not off since); otherwise caches of what the archive held, such as Alerts' history signatures, are rebuilt. Ordinary registrations through `ctx` are dropped when the plugin is turned off, and after that the context is inert: `settle`, `emit` and other calls do nothing. `activate` returns a disposer only for resources the plugin created itself (a queue, child processes). An activation must register everything its descriptor declares for its side: in core, a `serve` of each core call, a handler for each completion report, each rule kind, each AI provider and its search ranker; in main, a `serve` of each main call. A core activation missing one (or a descriptor with no core side declaring one) fails with an error naming what is missing, and its registrations are dropped as when it is turned off; a main activation missing one, or throwing, is logged (`plugin-activation-failed`) and registers nothing (`src/core/plugins/registrationCheck.ts`, `src/main/plugins/bundled.ts`). Declared completion reports (§3) let already-sent work finish without reactivating the plugin, through a finalizer rather than the context.

The renderer side is a declarative object: views and reactive functions the host's slots read while the plugin is on. It has no activate, because renderer state is module-level Solid state that lives for the window.

## 3. Extension point catalog

Every point is a typed interface in the SDK. **Slot** says where it surfaces. **Order**: host items first, then plugins' items in build order, unless a placement says otherwise (§6).

Panels owned by a known inactive plugin are omitted from both preset and custom layouts. The stored custom tree retains them. Structural edits apply to that full tree; displayed split paths map to stored paths and child indexes, so resizing preserves hidden shares. Removed owners still leave missing-panel placeholders. Renderer data reads use `pluginResource(plugin, member, args, fallback)` (or `pluginData(() => core.read(...), fallback)` outside a resource) to settle the deactivation race described in §5; `callable` alone cannot close that race.

### AI provider contract

The host owns per-provider enable, display names, model and thinking-level choices (`ai.providers[id]`), the aggregated model lists and plan-usage reads, and `ctx.ai` routing; all are keyed by declared id. A provider stays behind `LlmProvider`; no plugin reads or stores Claude or ChatGPT credentials (law 5). Claude and Codex spawn the user's signed-in CLIs; OpenRouter is paid through the host's OpenRouter keys, which stay in the host because Jev routes through them (`ctx.ai.openRouterKeys`).

- **Images.** A completion may carry `images` (base64 with its media type) and a `maxOutputTokens` cap. Only a provider declared with `images: true` takes them; the registry makes any other refuse such a request rather than answer without them. A model that reads images says so (`ModelOption.images`); Ollama reads it from `/api/show`'s `vision` capability.
- **Running.** A provider runs while its plugin is on and registered it. Providers handed out (`ctx.ai.provider`) are revoked when it turns off: later calls reject with the reason, and a running completion is aborted through its signal. Settings → AI shows a section per running provider in declared order, then plugins' sections on the AI page; with none, a note says so. A provider's own rows (an address) and availability note come from its renderer `providers[id]`.
- **Stored settings are lossless.** Normalizing keeps every stored provider entry whether or not the build has their plugin; declared providers a profile never set take `enabledByDefault`. Existing keys (`ai.providers.claude`, `.codex`, `.ollama`, `.openrouter`) keep their ids and values. There is no default provider (SDK 2.0): each feature picks its own in its settings (Summaries, Plans, Ask, Image text, Translation), using that provider's Settings → AI model and effort. The old `ai.defaultProvider` seeds each pick by shared settings-field adoption and is dropped on the next Settings → AI save. Ollama's address (`ai.ollamaUrl`) is parked in `legacy.ollamaSettings` by a migration, so a build without Ollama keeps it, and adopted into `plugin.ollama.settings`.
- **Default provider whose plugin is off or absent.** Requests use the first enabled provider that runs, in declared order (none: requests report "No enabled AI provider"). This fallback is not stored, so the choice returns with its plugin.
- **Features set to a provider that can't run.** A feature says why in its reply ("… is chosen for <feature>. Needs the X plugin, which is off.", or "which failed to start (see Settings → Plugins): <error>" when its activation threw; rule kinds are explained the same way) and never answers with another provider; the pick stays listed as unavailable in its settings. A stored summary names its provider by label, or by id when this build lacks it.
- **Local AI only.** Channels set to local AI only use the first declared `local` provider; with none running, requests for them say why. Host wording names the running local providers. Plugins' requests are held to it by their declared read scope (below).
- **Bundled providers and Plan usage.** Claude, ChatGPT (Codex), Ollama and OpenRouter are the plugins `claude`, `codex`, `ollama` and `openrouter`, declared in that (build) order. Plan usage (`usage`) owns the Plan usage panel (layout id `provider`, kept so saved layouts still place it), its phone drawer pane and the Display name row; without it the panel, pane and row are gone, and display names stay stored. The host reads each provider's plan usage when first asked (`planUsageOf`) and re-reads one after work it ran (`refetchPlanUsage(id)`); the panel asks for every enabled provider, the Summaries status bar for the default.

### AI read scope

Every AI request a plugin makes declares what it reads: `reads: readonly ChannelId[] | 'all'` (a thread by its own id). This covers `ctx.ai.provider(id).complete`, `ctx.jev.decider(feature).decide` and a folder plugin's `ai.complete` and `ai.decide` (PluginApi 2.0).

- **Checked at dispatch.** As a request is sent, the host checks the provider asked against each channel's effective policy (a thread inherits its parent's local AI only). A hosted provider or Jev is refused a local-only channel, and `'all'` while any channel is local-only; the request rejects with `LocalOnlyError` and nothing is sent. A Jev request is checked again just before each send, retries included, so one still waiting for a slot in Jev's queue is refused if a channel it reads turns local-only meanwhile. A local provider reads everything. A request without `reads` rejects with `TypeError` (folder plugins are plain JavaScript) (`core/ai/readScope.ts`; `tests/pluginReadScope.test.ts`).
- **Choosing sources.** `ctx.ai.sources.permitted(ids, reader)` keeps the channels `reader` may be sent, in order; `ctx.ai.sources.sql(column, reader)` is the same as a SQL condition on a channel-id column. `reader` is `'hosted'` (any hosted model, Jev included) or `{ provider: id }`. Plugins select with these and declare what they selected; the channel policy helpers themselves (`isLocalOnly`, `localOnlyChannelIds`, `assertHostedMayRead`, `hostedMayReadSql`) are host-internal.
- **Per-message Jev infers its scope.** Message questions and `ctx.jev.judgments.judgeNow` read the message's channel; the host already asks nothing of a local-only one. `boundDecider(decider, reads)` gives work whose requests all read the same channels (a summary run) a decider that declares them.
- **What it proves.** Declared reads are a central check against omission, not proof of where a prompt's text came from.

Callers: Alerts (dedupe reads both alerts' channels), Links (each link's first channel), Plans (the message's channel), Search re-rank (the channels of the hits it sends, as the archive has them, never as the caller claims), Summaries (the run's channels, for its provider and its Jev steps), Tags (range runs refuse a local-only channel; each message's judgment infers its own).
### Archive view contract

The paired views below have identical columns: `archive_<suffix>` applies live privacy; `archive_all_<suffix>` preserves every row. `archive_users` and `archive_rules` are single, privacy-neutral views. All 18 views are persistent, read-only, and use only built-in SQLite functions, including when reopened without application functions. They come from one registry (`ARCHIVE_VIEWS`, `src/core/archiveViews.ts`) that the host installs on every open, after any schema upgrade: a definition may read any host table, and changing one needs no migration. An upgrade drops them while its steps run (ALTER TABLE reparses every view) and installs them before it commits, so a failed upgrade keeps the previous views. A persistent object outside the registry must not read an `archive_` view, or an upgrade's ALTER TABLE fails on it. Privacy off includes every row, even through already-prepared statements. What privacy mode hides is the host's `hidden_ids` table (with its `hidden_channels` view), kept current by triggers on `settings`, `channels` and `guilds` (`src/core/hiddenScope.ts`); a migration that rebuilds one of those tables drops its triggers and must create them again.

Names are server nicknames expanded to channel/user pairs. Rules expose the stored namespaced managed key. Search exposes `query MATCH ?` and default bm25 `rank`.

Payload-derived fields use the typed `ctx.archive.payloads(ids)` reader, which decompresses stored payloads outside SQL views. It returns a map of `{ embedsJson, mentionsJson, bot, flags, isReply, replyToId, audioSeconds, kinds }`; missing messages are omitted, absent JSON fields are null, and `kinds` is a set. This reader preserves the selected ids' scope: display callers select through filtered views; background callers retain their existing unfiltered reads. Held contexts return an empty map after unload.

Plugin-owned archive references are declared as `archiveRefs: { localTable: { channel: 'channel_id', message: 'message_id' } }` (message optional), or `{ localTable: { channels: 'channel_ids' } }` for a JSON array. `visibleTable(plugin, localTable)` returns the host-owned `p_<plugin>_<localTable>_visible` name and rejects undeclared tables. These read-only views expose every owned table column. Single-message rows use the reference channel's visibility and, when archived, the message's original content; missing messages remain visible in visible or unknown channels. Channel-list rows show if empty or if any listed channel is not hidden. The host creates views after adoption and plugin migrations, validates them before activation completes, and rebuilds them transactionally around schema changes, including table replacements. A failed migration rolls both schema and views back.

Alerts declares its `alerts` table and reads its visibility view for the inbox, unread counts and mark-all-read scope. Summaries declares `summaries` and uses its visibility view for history, retaining text/citation redaction. Plugins cannot apply `privacy_visible`, `reference_visible`, `hidden_channels` or `hidden_ids` predicates themselves; `plugin:check`'s scan rejects those identifiers.

The all-data allowlist, with one reason per file (`<plugin folder>/<path>`), is `scripts/pluginScan/allReaders.ts` for the public marketplace's plugins, plus a plugin repo's own `all-readers.json` (same shape, beside its `plugins/` folder), whose owner answers for its grants. Exceptions preserve unfiltered background work, exports, AI input, scope metadata, live Discord chips, and link share counts/previews. Adding an all-data reader requires updating one of those lists; `plugin:check` refuses an unlisted reader and a listed file that reads none. No plugin may write an archive or declared visibility view, or access a host table, including through a dynamic table name. A plugin that took over a host action kind declares `adopts.actionKinds: { oldKind: '<plugin id>.<name>' }`; host adoption alone converts legacy action-run kinds, including rows written after host migration and while the plugin is disabled.

### Renderer controls used by extracted features

`RuleTemplate.make()` may return a `trigger`; omission keeps the message trigger. Shortcuts may declare `hintGroup`: adjacent hints in that group combine keys, preserving per-key handlers and placement. A shortcut may declare `name`, what its one key does: Settings → Desktop lists it by that, in sentence case, instead of the hint its group shares.

`rules.managedControls` maps an owner's local managed-rule keys to a reactive `locked()` and `setEnabled(on)`, with an optional `feature` naming the Jev switch it replaces (one it declares; the host stamps it). Only active owners control their namespaced keys. `rules.activity(rule)` contributes text to the rule activity summary. `rules.ruleBadge` continues to render list badges.

`RuleTemplate` accepts an optional stable `id` and `before`/`after` placement, using the shared anchor helper; unknown anchors append. `notificationKinds` contributes a labelled, placed choice for each declared notice kind while active: a choice on the phone's pairing sheet, and, with `desktop`, the subject, lede sentence and hint Settings → Notifications shows for the desktop switch. Notification routing and persisted choices remain host-owned.

Shared rule declarations may mark an action `defaultForNewRule`; the first in editor order seeds a fresh draft, or it starts empty. `managedRules` supplies validators keyed by local managed-rule key. Validation follows namespaced keys (and declared adoption aliases) even when disabled; absent owners retain stored shapes unchecked, as for absent kinds. Managed edits also preserve trigger, match and narrowing in the host store. `jevFeatures` supplies renderer wording and costs for a plugin's declared Jev switches.

Settings-field adoption: `adopts.settingFields[]` declares `{ key, field, name, shared? }` to move a legacy JSON field into the same field of a plugin preference. Adoption preserves an existing destination field, removes the legacy source field (kept when `shared`, for the other plugins adopting it), and runs transactionally and idempotently even while the plugin is disabled.

Jev feature controls: renderer `jevFeatures[key].Body?: Component` adds controls after that feature's query list. Its lifecycle follows the active feature owner. A window reads or sets a switch with `jevSwitch(plugin, key)` (kit): `on()`, `locked()`, `set(on)`; it never reads Settings → AI's `jev` by stored key.

## 5. Channels

One contract per plugin, declared in `shared` with **audiences**. It replaces `rpc.handle`, `fromMain`, `toMain`/`onCore`, `pluginMain.invoke`, `events.emit`/`onPluginEvent` and the separate phone allowlist.

| Section | Served by | Audiences |
|---|---|---|
| `core` | core `ctx.channels.serve` | `renderer`, `phone`, `main` |
| `main` | main `ctx.channels.serve` | `renderer` |
| `events` | emitted by core `ctx.channels.emit`, or main `ctx.channels.emit` for `renderer`/`phone` audiences | `renderer`, `phone`, `main` |

`checkBundled` holds each member to its section's audiences (`SECTION_AUDIENCES`): at least one, none outside the section's, no other section, and completion reports (§3) only in `core`, main-only.

**The phone's wire.** Desktop IPC and the utility-process channel stay structured clone. The phone transport carries JSON through one codec, `encodeWire`/`decodeWire` in `@plugin-sdk/shared` (`src/shared/wire.ts`), which the phone transport's page and server both use: bytes travel as `{ $u8: base64 }` and arrive as `Uint8Array` (a Node `Buffer` included), and `undefined` as `{ $void: true }`, so a void result round-trips as `undefined` and an undefined array element or property arrives present (never an array hole a decoder's `every` would skip). What the phone sends or receives is typed to `WireValue`: `defineChannels` refuses, by type, a member whose audiences include `phone` when an argument, result or event payload has a part that isn't one (a `Date`, `Map`, function, class instance with methods, `bigint` or `unknown`); desktop-only members keep any structured-cloneable shape.

**Phone writes.** A core call the phone may make is declared `{ audiences, writes, decode? }`: `writes` states whether it changes anything, and one that writes needs `decode(args)`, which checks and shapes its arguments and throws the reason they are refused. Both are enforced by type (`defineChannels`) and by `checkBundled`. The host runs a declared decoder before the handler for every origin (`ctx.channels.serve`); elsewhere decoders are optional. Alerts' `markRead` and Summaries' `summarize` are the phone's writes.

- Clients are typed to their audience. Main's `ctx.channels.core` has only members whose audience includes `main`. In the renderer, `desktopCoreClient(plugin)` has exactly the members for `renderer` (code only desktop windows run), `phoneCoreClient(plugin)` exactly those for `phone`, and `coreClient(plugin)`, for code either window runs, has the members both serve directly and one window's alone as optional: at run time a member this window's audience lacks is undefined (the preload's windows are `renderer`, a page without it `phone`). `callable(plugin, name)` says whether this window may call one now (the plugin is on and the member lists this window). `onEvent(plugin, name, fn)` is typed to the event's payload.
- `pluginResource(plugin, member, args, fallback)` is a core read as a Solid resource: it reads while `callable` and `args()` gives the member's arguments, re-reads when either changes, and reads as `fallback` while the member isn't callable or `args()` gives none (not the last answer), and when the plugin turns off mid-read, whether the switch or core's inactive answer arrives first. Other failures keep their message in `.failure`; `.refetch()` evaluates `args()` again (Solid's reuses the last arguments, so a `Date.now()` window would go stale); `.loading` and `.mutate(value)` are Solid's.
- **Origins are stamped by the transport, never claimed.** Main's IPC handler stamps `renderer`, the phone transport's gateway (main/phone/hub.ts) stamps `phone`, and main plugins' client stamps `main`. Core checks the origin against the descriptor before it runs a member; folder plugins' calls (public `PluginApi`) accept `renderer` only.
- Main fans each plugin event out to exactly its audiences: windows, the phone, and main plugins' `ctx.channels.on`. Core → main requests are events with audience `main`, so they never reach a window.
- `serve` must implement exactly the declared members (checked by type). A member is served once, whatever its audiences.
- Core throws the exported `PluginInactiveError` when a known plugin is inactive. Its service boundary returns `{ status: 'inactive', pluginId }`; successful calls return `{ status: 'ok', value }`. The utility-process channel, Electron IPC and the phone's HTTP transport (the wire codec above) carry this envelope intact. Renderer `coreClient`/`mainClient` and main's `ctx.channels.core` unwrap through `clientOver`, restoring `PluginInactiveError` without parsing messages. Folder panels' `PanelApi.call` also unwraps. Main-side calls use the same success envelope; main sides remain running when core stops.
- `pluginData(read, fallback)` in the renderer SDK resolves only `PluginInactiveError` to the caller's fallback and rethrows all other errors. Use it for resources, paged reads and event-driven data refreshes. Unknown members, forbidden audiences and failures inside a handler retain normal transport rejections. Declared main completion reports (§3) remain callable after disable so already-started work can finish: the host checks each against its ledger of issued keys, and the handler writes only through its finalizer, closed once it returns. A window's call to a plugin's main side is refused centrally with the inactive envelope while core's list (read at call time) has the plugin off; main's event listeners, which carry completion reports, stay.

## 6. Placement

`after: Anchor`. The host's anchors are id lists in `@shared/anchors` (`HOST_PANELS`, `HOST_SETTINGS_TABS`, `HOST_RULE_TEMPLATES`, `HOST_SETTINGS_PAGES`, `HOST_SHORTCUTS`, `HOST_TOP_BAR_ITEMS`, `HOST_PHONE_SECTIONS`, `HOST_PHONE_DRAWER_ITEMS`, `HOST_PROVIDER_ROWS`, `HOST_CHAT_FOOTER_ITEMS`, `HOST_HOVER_EMOJI_ITEMS`, `HOST_HOVER_ACTIONS`), and the host's own UI is typed against them. A plugin panel may also anchor on another plugin's panel id. `checkBundled` rejects unknown anchors and cycles at build time, resolving panel, settings-tab and shortcut anchors through every plugin folder's declarations: a build that leaves plugins out gets their anchors as a catalog (`bundledPlugins.ts`), so leaving an anchor's owner out is not a typo. Plugins installed separately may anchor on one not installed: a stamped anchor (`<plugin>.<item>`) on a plugin that isn't here is no typo, and one on a plugin that is here must name its item; an unstamped one (panel, Settings tab, shortcut) nothing here declares is a typo only where every plugin that could declare it is here (a build, a release, plugin:check), and is accepted among installed plugins (`UnknownAnchors` in `bundledCheck.ts`). `checkBundled` checks only the listed plugins' anchors; the catalog says what they may name and which plugins are here (`AnchorCatalog.plugins`, so one declaring nothing stamped still counts). Each plugin answers for its own anchors: a broken plugin left out of a build, or a sibling in plugin:check, fails no other, and installed plugins are checked against every candidate, so a bad anchor refuses its own plugin whatever the load order. One ordering function places every slot's items: when an anchor is missing (its plugin off or not built), the item follows the anchor's own anchor, and at the end when none remains.

**Slot items** (top bar, status bar, phone sections and drawer, provider-card rows, message-menu groups, Archive footer, hover-bar reactions and actions, rule templates, person sections) are declared in the descriptor, component-free: `slots: { <slot>: [{ id, after?/before? }] }`, with one `Placement` type (one direction or none; panels keep their required `after`/`before`). The renderer side gives a view for exactly each declared id, `<slot>: { [id]: view }`: the type requires it, and installing the registry refuses a missing or undeclared view (`checkSlotViews`). The host stamps each item `<plugin id>.<local id>` (`slotId`), so plugins can't collide with each other or with the host's bare ids; an anchor names a host item of the same slot or another item's stamped id. The catalog (`AnchorCatalog.slots`, `anchorCatalog`) holds every declared item's anchor by stamped id; building it refuses an item declared twice, and `checkBundled` refuses a local id that isn't an identifier, both directions, an anchor no item of that slot provides, and a cycle, over the complete catalog, message-menu groups included. These are pure functions of a descriptor set: the build runs them over every plugin folder (the catalog a partial build emits), and a set installed at run time validates the same way.

Layout presets may name a plugin's panel; while that panel is unavailable the preset leaves it out and its split closes up. A custom layout keeps the panel's place and shows its missing-panel note, since the owner put it there.

## 7. Data and adoption

- Tables are `p_<id>_<name>`, preferences are stored as `plugin.<id>.<name>` (a plugin reaches no other setting), and files go in the data folder. A main side's secrets are `<profile>/secrets/<id>-<name>`, so a feature's files named `<id>-…` before extraction need no rename.
- **Adoption** is declared, not coded: `adopts: { tables: { old: 'name' }, settings: { oldKey: 'preference' }, dataDir: 'profileFolder' }`; an adopted setting lands on a declared preference (type and checkBundled). The host runs each rename at startup for every plugin in the build, on or off, so data never depends on the switch. A rename runs only while the old name exists and the new one doesn't, so it is idempotent. Data fixes (rewriting stored values) stay as the plugin's own `migrate` steps.
- Host data that other host features read, such as derived text or the link index, stays in host tables. A plugin writes to them only through an extension point.
- Jev switches and notice kinds are stored stamped, `<id>.<key>` and `<id>.<kind>`. `adopts.jevFeatures` moves a pre-plugin switch at startup; the old value wins, since normalizing fills a stamped key with its default and a save stores it, while an old key exists only until adopted. `adopts.noticeKinds` maps a phone's pre-plugin choice whenever it is read or subscribed. A switch or phone choice whose plugin is absent is kept (normalizing keeps every stored switch with an identifier or stamped key; phones keep stamped and pre-plugin kinds), so uninstalling and reinstalling a plugin loses nothing. Every check is a pure function of the installed descriptors.
- Managed-rule adoption is declared as `adopts.managedRules: { oldKey: 'localKey' }`. Startup updates only `rules.builtin`, to `<plugin id>.localKey`, leaving ids, armed times, owner edits and related rows intact. An existing destination key leaves both rows unchanged. Duplicate legacy owners or destinations and invalid local keys are rejected by `checkBundled`.
- Phone section adoption is declared as `adopts.phoneSections: { oldId: 'localId' }`: ids a phone stored before slot ids were stamped (its last section in session storage; a delivered notice's panel target, which the service worker replays) resolve to `<plugin id>.localId` when read (`adoptedPhoneSections`, `phoneSectionFor`), since the host can't rewrite what a phone keeps. Each plugin brings its own; two plugins claiming one old id, or a destination that isn't a declared section, are rejected by `checkBundled`. Alerts adopts `alerts` (→ `alerts.inbox`), Summaries `summary` (→ `summaries.summary`). Saved desktop layouts store panel ids, which slot ids don't replace, so they need no adoption.

## 8. Lifecycle and failure

The states are `disabled → active | error`, shown in Settings → Plugins with the plugin's contributions, read from its descriptor.

A throw inside any registered callback is recorded on the plugin and isolated. What the caller sees depends on the point: a provider's result is left out, a listener is skipped, and a rule action records a failed run. Turning a plugin off drops its registrations, and the host re-renders its slots.

Each activation has a lifetime (`ctx.lifetime`). Turning the plugin off aborts it: providers from `ctx.ai.provider`, Jev from `ctx.jev.decider` and `judgments.judgeNow` get the abort through their signal, reject at once with `PluginInactiveError` (even when the callee ignores the signal), and drop an answer that arrives after; Jev never sends a request still waiting for a slot. The context's services are inert after unload, and a folder plugin's held `PluginApi` likewise (registrations, settings writes, notices and annotations do nothing; AI calls reject; statements that write through `api.db`, even ones prepared earlier, and `api.db.migrate` throw `PluginInactiveError`); its queued message callbacks don't run. The effects a core plugin holds are fenced by the host: writes through `ctx.storage.db` (a statement or transaction function prepared earlier included; `pluck`/`raw`/`expand` return the fenced statement), `ctx.storage.migrate`, `ctx.archive.store()` handles, and `ctx.net.fetch`, which settles with `PluginInactiveError`; reads stay open. Plugins fence their other async continuations with `ctx.lifetime.fence` or the signal (a thrown `PluginInactiveError` is the expected end: Plans leaves its hit pending). A main resource's run (`ctx.whileActive((run) => …)`) ends before its disposer runs, and `run.secrets`, `run.net.fetch` and `run.emit` refuse the same way, so a server's late work can't act for the next run. A completion (`ctx.ai.provider(id).complete`) also settles at once when its own `signal` aborts, so awaited work gets a named deadline (`deadline(ms)` from `@plugin-sdk/core`) and a stalled provider never holds a plugin's queue: a Plans extraction (`PLAN_EXTRACTION_DEADLINE_MS`).

Work that outlives an activation is kept in module-level session state (one per core process), bounded, and never in the activation: queued work pauses on disable and the next activation resumes or reconciles it (Links X posts, transcript downloads), and work already handed outside the plugin (Discord posts and replies, audio downloads) is finalized by its completion report, or at its deadline when main never reports (a download's `DOWNLOAD_REPORT_MAX_MS`: the job fails through the activation running then, or, while off, stays fetching and the next activation queues it again). Outstanding work stays within each report's declared `max`: Transcription's downloads (`AUDIO_FETCHES_MAX`) by waiting for a report before sending more. Cooldowns, claims and budgets also live there. Queued work that must survive a quit is stored in the plugin's own table instead: Plans' hits still to extract (`p_plans_pending`) resume on the next activation, whether it follows off and on or a restart.

Folder plugins keep the versioned public `PluginApi` (2.0: AI requests declare `reads`; `query.messages` and `query.channels` read `archive_messages` and `archive_channels`, so privacy mode applies; a 1.x plugin is refused with what changed). Their raw SQL (`api.db`) is full trust and reads anything.

## 9. Enforcement

- The app holds no plugin code. Host code imports by path only inside `src/`, and reaches plugins only through the virtual registries (`tests/bundledPlugins.test.ts`).
- Plugins import only `@plugin-sdk/*`, their own folder and packages; of the renderer SDK, only its four tiers, and `/shell` only in the phone transport's plugin. These and the other source rules are `plugin:check`'s scan (§16; `tests/pluginScan.test.ts`, over fixture plugins). The installed build also refuses host internals.
- No renderer SDK tier loads the plugin registry, a page entry or a plugin, however indirectly, and the contract loads nothing of the host but `@/api` (`tests/rendererBoundary.test.ts`, over the transitive import graph). Host slots read plugins through an accessor the registry installs (`plugins/installed.ts`), so the SDK initialises first in every entry order: the app's page, the phone's, the SDK or the registry first, or a plugin alone (`tests/rendererInit.test.ts`). One app-event subscription and one plugin list serve host and SDK readers (`tests/rendererSharedState.test.ts`).
- `checkBundled` validates descriptors: ids, namespaces, anchors and channel audiences.
- Contract tests per extension point, run against a probe plugin. Audiences: core serves each member only to the origins it lists (`tests/pluginSdk.test.ts`), the phone gateway stamps and refuses (`tests/pluginPhone.test.ts`), and renderer clients hold only this window's members, by type (`src/plugin-sdk/renderer/clients.typecheck.ts`) and at run time (`tests/rendererClients.test.ts`).
- The phone's wire: phone shapes are WireValues and its writing calls have decoders, by type (`src/plugin-sdk/shared/wire.typecheck.ts`) and at run time (`tests/pluginWire.test.ts`).
- Styling: a plugin's CSS holds structure only, with tokens; its look is the theme's look vocabulary (§14, test).
- Testing: the harness's public types name only SDK entries, and no app module imports a testing entry, so none is bundled (§15, `tests/pluginTesting.test.ts`).

## 10. Alternatives considered

- **Keep the current shapes and rename them.** Rejected: plugins would still reach about 60 host-internal modules, register in three styles, and use six transports.
- **VS Code-style JSON contributions with activation events.** Rejected: bundled plugins are compiled in, so typed descriptors check at build time what JSON could only check at run time, and lazy activation is unnecessary.
- **One `Plugin` object per process with optional fields (the old renderer entry).** Rejected: nothing ties a declaration to its implementation.
- **An `activate(ctx)` in the renderer too.** Rejected: renderer state is module-level and lives for the window, so registration would only copy a static object into the same registries.
- **Origins claimed by the caller (`pluginCall(origin, …)` from the renderer).** Rejected: a window could claim `main`.

## 11. Migration

1. **SDK and adapters** (done). `@plugin-sdk/*` and `@shared/anchors`; `define*Plugin` first adapted the new contexts over the old host internals.
2. **Port the first plugins** (done): exchange, stats, plans and transcription among them, in the same commit as step 1 so every commit builds. Their adoptions became declarations.
3. **Collapse** (done). The registries read descriptors directly: one call map with stamped origins, one event type fanned out by audience, one ordering function, declared adoption (replacing `LEGACY_DIRS` and the rename migrations). `CoreHost`, `MainHost`, `RendererPluginEntry`, `BundledShared`, `rpc`/`fromMain`/`toMain`/`phone` are gone; the SDK-only import test is in.

## 12. Rules

Rules are the host feature the most plugins build on: Tags, Alerts and Summaries each add rule parts. So every rule part is a registered **kind**, and the host's own kinds are registered through the same registry as plugins' kinds. Nothing in the engine, the editor or validation branches on a specific kind.

### 12.1 Spec v4

```ts
interface RulePart<C = unknown> { type: string; config: C }
interface RuleSpec {
  v: 4;
  trigger: RulePart;                         // what starts the rule
  gates: RuleGates;                          // where, who, edits, missed: unchanged, not a part
  match: RulePart[];                         // any one is enough; empty: the gates and narrowing decide
  narrow: RulePart[];                        // every one must hold
  actions: (RulePart & { id: string })[];    // in order
}
```

- A type appears at most once in `match` and at most once in `narrow`. Action ids are unique.
- **Type names.** The host's kinds are unprefixed. A plugin's kinds are `<plugin id>.<name>` (checkBundled). A stored rule whose plugin kind this build lacks keeps loading and editing; unavailable conditions and skipped actions name the plugin.
- **At most one Jev-asked match part.** v3 asked only the Jev question when a rule had both a question and a meaning. The upgrade keeps just the question, so behavior is unchanged.

### 12.2 Kind declarations (shared)

```ts
interface RuleKind<C, T extends string> {
  type: T; label: string; hint: string;
  create(): C;
  validate(config: C): void;                 // throws a message for the editor
}
interface RuleTriggerKind<C, T> extends RuleKind<C, T> {
  /** 'message': fires on one message (gates, narrow and match apply). 'window': runs on a stretch of time. */
  event: 'message' | 'window';
}
interface RuleMatchKind<C, T> extends RuleKind<C, T> {
  /** Asked of Jev: needs the 'message' trigger, since Jev is asked as a message arrives. */
  asksJev: boolean;
}
type RuleFilterKind<C, T> = RuleKind<C, T>;
interface RuleActionKind<C, T> extends RuleKind<C, T> {
  targets: readonly ('message' | 'window')[];   // what it can act on
  phase: 'match' | 'after';                      // 'match': runs synchronously when the rule fires, before 'after' actions
  history: boolean;                              // also acts on matches older than the rule (no run recorded)
  minIntervalMs: number | null;                  // per rule action on message runs; a run still going also blocks
  actsAsYou: boolean;
  liveOnly: boolean;
}
```

- The descriptor groups them as `rules: { triggers?, match?, filters?, actions? }`, which replaces `ruleActions`. `defineRuleTrigger`, `defineRuleMatch`, `defineRuleFilter` and `defineRuleAction` preserve literal types and configuration types in `@plugin-sdk/shared`.
- `checkBundled` requires `<plugin id>.<name>` (a nonempty identifier suffix), unique across every section, plugin and host kind. Plugin triggers must have `event: 'message'` in R2: scheduled-window implementations remain host-owned until a later phase.
- R1's supported action floors remain `null`, `MS_PER_MIN` and `MS_PER_HOUR`; registration rejects other intervals to retain existing pacing wording and validation.
- `RuleTriggerTypes<D>`, `RuleMatchTypes<D>`, `RuleFilterTypes<D>` and `RuleActionTypes<D>` select declared names; `RuleConfig<D, Section, Type>` selects their configuration.
- The host's kinds are the same objects, in `src/shared/ruleKinds/`. The registry (`ruleKind(section, type)`) places bundled kinds using optional `after` or `before` kind types and the shared anchor resolver (unknown anchors append; declaring both directions is rejected), so validation, `actionInfo`, `runsOnMissed` and `actsAsYou` read one place.
- Schedule validation uses window-capable action labels through `windowActionsText`.
- Stored or edited rules preserve absent plugin parts. Strict `validateRuleSpec` still rejects missing declarations by default; loading and saving opt into `allowMissing`. Unavailable trigger, match or filter implementations prevent compilation and the rule list explains which plugin is off or absent. An unavailable action records `skipped` with that reason while other actions continue.
- **Cross-part checks stay in the host** (`validateRuleSpec`):
  - A match part with `asksJev` needs the `message` trigger.
  - A `window` trigger allows no match, narrow or authors, and only actions whose `targets` include `window`.
  - A `message` trigger allows only actions that target `message`.
  - Actions with `actsAsYou` need `discordSend`.
  - Managed rules keep their match.

A plugin declares a window-capable action with `targets: ['message', 'window']` (or only `window`) and `phase: 'after'`. No feature name participates in scheduling or validation. Its callback branches on `r.event.kind`; window actions receive the scheduled range and timing. Disabling or omitting the owner retains the stored part and R2's unavailable explanation, while other window actions continue. Each action of a timed rule keeps its own progress: an unavailable one sits out without consuming its window (an app-start one stays owed across quits, in the `rules.owedAppStarts` setting, until it runs or the rule is re-armed), the others run alone (run key `<due key>#<action id>`), and it catches up from its own last run once back (an every-N-hours one under `time:catchUp:`, which doesn't move the rule's schedule, so it then runs with the others again). A run key without the mark ran every action.

| `lastDone`, `attemptsSince`, `update` | Unchanged. |

- Registrations are scoped to the plugin's own declarations and disposed on disable; the engine recompiles after activation and disposal. Held contexts become inert. Expected operational failures return `{ outcome: 'failed', detail }`. Throws and rejected actions indicate plugin faults and are recorded by the existing plugin hook guard only while the activation is live. Failed match callbacks return no match, failed filters return false, and failed preparation excludes the rule from compilation. A returned question's answer matcher is guarded too.
- Match and filter `prepare(config)` runs once per rule compilation and its result is passed to the implementation callbacks; it never changes the stored config. This retains R1's prepared-regex/cache path.
- **Message questions.** `QuestionContext` gains `mayAct(actionType)`. It is true when a rule with an action of that type fired on this message directly, or is waiting for Jev. Alerts' urgency question asks only then.
- **Firing order** (unchanged semantics):
  1. Claim the run for the event key.
  2. Run the `match`-phase actions synchronously and record them.
  3. Run the `after` actions asynchronously, in order.
- **Messages older than the rule**: only when the rule has a `history` action, and held to where/who only. Those actions run with `history: true` and no run is recorded.

## 14. Styling: structure and look

Decision: the host theme owns how things look; a plugin's CSS only lays out its own elements. A plugin's CSS modules (`plugins/<id>/**/*.css` in its repo, its page included) hold **structure**. The **look** comes from the theme's look vocabulary, applied as classes in the plugin's TSX beside its structural class. The theme never names a plugin: roles are semantic, and colours that depend on where an element sits read `--cp-section` (the nearest `[data-section]`) or `--cp-platform` (the nearest `[data-platform]`).

### Property sets

| Set | Properties | Owner |
|---|---|---|
| Structure | `display`, `position`, `inset` and its sides, `z-index`, `isolation`, `float`, `clear`; `flex*`, `order`, `grid*`, `gap`, `row-gap`, `column-gap`, `align-*`, `justify-*`, `place-*`; `width`, `height`, `inline-size`, `block-size` and their min/max, `aspect-ratio`, `box-sizing`; a field's `field-sizing` and `resize`; multi-column flow (`columns`, `column-count`, `column-width`, `break-inside`); `margin*`, `padding*`; `overflow*`, `overscroll-*`, `scroll-*`, `scrollbar-gutter`; `object-fit`, `object-position`; text flow (`text-align`, `white-space`, `text-overflow`, `word-break`, `overflow-wrap`, `hyphens`, `text-wrap`, `vertical-align`, `line-clamp`, `-webkit-line-clamp`, `-webkit-box-orient`); `visibility`, `pointer-events`, `touch-action`, `user-select`, `-webkit-touch-callout`; `content`, `counter-*`, `list-style`; `container*`, `contain`; `translate`, and `transform` when it only translates | A plugin's CSS module |
| Look | `color`, `background*`, `border*` (width, style, colour and radius), `outline*`, `box-shadow`, `opacity`, `filter`, `backdrop-filter` (and `-webkit-backdrop-filter`), `cursor`, `appearance`, `accent-color`, `caret-color`; typography (`font*`, `line-height`, `letter-spacing`, `text-transform`, `text-decoration*`, `text-shadow`); `transition*`, `animation*`; `fill`, `stroke*`, `mask*`; `rotate`, `scale`, any other `transform`; `mix-blend-mode`, `scrollbar-color`, `scrollbar-width`, `color-scheme` | The theme (`src/renderer/src/theme/`) |

Borderline calls:
- Text flow is structure: it decides where lines break, not how glyphs look.
- Generated content, counters and `list-style` are structure: they decide which boxes exist, as `display` does.
- `translate` (and a translate-only `transform`) moves a box, as `inset` does, so it is structure (a drawer's closed position, a pull's offset). `rotate`, `scale` and other transforms are effects.
- `line-height` and `letter-spacing` are typography, so look, though they change a box's height.
- `appearance` removes a native control's drawing, so it is look.

Values in a plugin module are tokens (`var(--…)`), keywords, zero, counts (unitless numbers: flex factors, grid spans and repeats, `calc` multipliers) and proportions (`%`, `fr`); never a length, time, angle, colour or text. Strings only name grid areas or generated content. A container query's condition can't read a custom property, so its literal stays, commented where used. A plugin may set a custom property unless a look declaration anywhere reads it, directly or through another custom property: re-scoping embed or header geometry (`--cp-embed-thumb`, `--cp-header-grow`) is structure; `--cp-tag-color` is look.

`plugin:check` and the installed-plugin build enforce this on each plugin's stylesheets (`checkStyles`), and `tests/pluginStyles.test.ts` on fixture plugins' (the sets are the named constants in `src/main/pluginBuild/cssRules.ts`, which the installed-plugin build checks with too, §16), and checks that the vocabulary sets look only. Structure and look therefore never set the same property on an element, so the order in which a plugin's module and the vocabulary load can't change what wins.

## 15. Testing

A plugin's tests start its sides under the host's own adapters, never a permissive fake context. Each process has a testing entry; only tests import them.

| Entry | Starts | Over |
|---|---|---|
| `@plugin-sdk/core/testing` | `testPlugin(definition, options?)`: a core side (or a bare descriptor) | The plugin host, AI registry and read scope, archive, rule kinds, completions, and the transports' envelopes and codecs |
| `@plugin-sdk/main/testing` | `await testMainPlugin(main, core, options?)`: a main side over a core harness | Main's starter, plugin states, notification policy, phone gateway and live labels |
| `@plugin-sdk/renderer/testing` | `testWindow({ audience, core, main? })`: the window a renderer side runs in | The SDK's own clients, over an in-memory transport stamped with `audience` |

```ts
const t = testPlugin(statsCore, { archive: { channels: [{ id: 'c1' }], messages: [{ channelId: 'c1', content: 'hi' }] } });
onTestFinished(() => t.dispose());
await t.client('renderer').activityStats({ scope: 'all', channelId: null, sinceTs: null });
const main = await testMainPlugin(exampleMain, t, { dialogs: { pickFiles: async () => [file] } });
await main.client().pickFiles();
```

- **Calls and events** are typed from the descriptor. `t.client(audience)` holds exactly the members that audience (`'renderer'`, `'phone'` or `'main'`) may call, and carries them as its transport does: structured clones for a window or main, the wire codec through the phone gateway. `t.events(name)` lists what the plugin emitted; each process gets its own copy of an event, as the app's transports carry it. `main.client()` is a window's calls to the main side.
- **Switches.** `await t.off()` and `await t.on()` switch the plugin as Settings → Plugins does, and resolve once the host and any linked main side did. `t.restart()` ends every activation and starts a new core over the same profile.
- **AI.** `ai.providers` are scripted `LlmProvider`s, declared and registered as a provider plugin's would be (`local` for one that runs on this PC). `ai.jev` is the Jev decider, and `ai.switches` are the Settings → Jev switches (the plugin's own by local key). Completions still pass the read scope, so a hosted provider is refused a local-only channel.
- **Network.** `network` stands in for the wire behind `ctx.net.fetch`. Each hop still passes the descriptor's policy (declared hosts, owner-set addresses, never Discord). Unset, requests reject.
- **Clock.** `clock` is the host's clock (rule runs, session times). `ctx.session.lastSeenAt()` is the previous session's time as core reads it at start: the profile's `session.lastSeenAt`, else a day before the clock; each start records the clock as this session's.
- **Fixtures.** `archive` seeds servers, channels (`localOnly`, `hidden`, threads by `parentId`), history from plain rows, and privacy mode. `t.archive.arrive(rows)` delivers live messages, and `setChannel` and `setPrivacyMode` change privacy later, through core's own handlers and their events. `profile` holds settings and SQL an earlier version left, for `adopts` to take over. `preferences` and `self` set the stored preferences and the signed-in user.
- **Reading back.** `t.db` is the archive as the plugin's reads see it. `t.status()` is the Settings → Plugins row (`t.status(id)` another installed plugin's). Rule kinds are the host's and the installed plugins', so a plugin outside the build's registry registers its own. `t.rules.unavailable` and `t.ai.unavailable` give the host's reasons, and `t.mediaDir` is the media store. On the main side, `main.notifications()`, `diagnostics()`, `secrets()`, `synced()`, `labels(channelId)` and `route(name, request)` read back what main did. Main's stand-ins are `dialogs`, `discord`, `network`, `emojis`, `attachments` and `secrets`.
- **Windows.** `testWindow` makes one window per test file, since the renderer SDK keeps one API per page. A `'renderer'` window has the desktop preload's API. A `'phone'` window has the phone page's API over the gateway. With `main`, a window hears events as the app's do, through main's router: core's and main plugins' events for windows, or what the phone hub hands its transport. Without `main`, it hears core's events straight, filtered the same way. Import the renderer entry by path (the node type-check doesn't follow renderer modules). Mock `solid-js` with its client build (`solid-js/dist/solid.cjs`) when a test reads resources or effects.
- **Links.** `t.link` and `main.link` are opaque. A main or window harness reaches its core (and main) through them, so the renderer entry never imports core or Node code.

The public types import only SDK entries (`tests/pluginTesting.test.ts`). Three tests there fail if the harness bypasses the host: a fence after `off()`, a hosted provider refused for a local-only channel, and a phone-only member absent from a desktop window's client (`tests/pluginTestingWindow.test.ts`).

Not driven by the harness (a test drives them directly):

- The rule engine: `t.rules.run` runs one action.
- Jev's per-message matcher: answer a registered question through `messageQuestions()`.
- Link index rebuilds and host settings saves.

Core serves windows the plugin calls, the host's plugin methods (`plugins`, `setPluginEnabled`, `reloadPlugins`, `runPluginCommand`), the archive methods (`directory`, `messagePage`, `setChannelPolicy`, …), `getSetting`, `setSetting` and `lastSeenAt`. Text retention isn't modelled: a channel's text tier changes nothing stored. Any other host method rejects, naming it. A phone window's plugin calls are gated by the bundled registry (`phoneMayCallPlugin`), so a probe plugin that isn't bundled is refused there; `t.client('phone')` goes through the gateway without that gate.

## 16. Installed plugins

Descriptor plugins built outside the app's build, installed into the profile and loaded at start. They use the same SDK, checks and registries as bundled ones; only where their code comes from differs. The contract is `src/shared/installedPlugins.ts` (built output) and `src/shared/marketplace.ts` (marketplaces). Plugins run with full app privileges, as bundled ones do: the SDK guards against mistakes, not hostile code, and only the owner publishes.

### Built output

One function builds a plugin folder into an output folder; release assets, source installs and local folders all produce it, and the loader reads only it.

```
<id>/
  plugin.json   InstalledManifest: format, id, name, version, description, sdk, node, browser (page optional), hostImports
  source.json   InstalledSource: release (repo, tag, sha256), source (repo, branch, commit) or local (path)
  node/         ES modules for core and main: shared.js, core.js, main.js, chunks/
  browser/      ES modules for windows and the phone page: shared.js, renderer.js, chunks/, and its stylesheets;
                with a page: page.html, page.js and public/
```

- **Source.** `parseInstalledSource` reads source.json, checking each kind's fields (repo, sha256, commit, `installedAt`); a missing or malformed one reads as none, which only leaves updates without a source.
- **Folders.** `INSTALLED_PLATFORM_DIRS` names `node/` and `browser/`: the build writes each platform there, `parseInstalledManifest` refuses an entry or stylesheet outside its platform's folder, and windows are served `browser/` only.
- **Host modules.** A build leaves out `HOST_MODULES` (the SDK tiers and `solid-js`, by platform) and reads the host's instances from `globalThis[HOST_MODULES_KEY]` through generated shims, so a plugin never carries a second SDK or Solid runtime. It records each host export it imports (`hostImports`); the loader refuses a plugin whose imports this host lacks, naming them. Everything else a plugin imports is bundled. `node:` built-ins stay imports. Each platform's processes publish all of its `HOST_MODULES`: the shared step `SHARED_HOST_MODULE`, then the tiers, typed complete (`TierHostModules` in the browser, `NODE_TIER_PUBLISHERS` in `bundledPlugins.ts` on node), so a module left out is a type error; `tests/installedContract.test.ts` checks the published set.
- **SDK version.** `sdk` is the `PLUGIN_SDK_VERSION` it was built against. The host runs it when the major matches and its minor is no newer (`sdkMismatch`). A change that removes or changes an SDK export (or a context member) raises the major; an addition, the minor. `tests/sdkSurface.test.ts` records each SDK module's export names (`tests/fixtures/sdkSurface.json`) and fails on a change the version doesn't follow; once raised, `UPDATE_SDK_SURFACE=1` records the new surface. Context members (`ctx.*`) aren't exports, so review holds them to the same rule. An optional request field an older host ignores (`aboutChannels`) needs no bump: such a plugin still runs there, unmuted as before. 1.1.0 added installed pages, `SegButton`/`SegGroup`, `ctx.discord.humanPause` and notification mutes (`notificationMuted`, `mutedPlaces`). 1.2.0 added the directory's DM state: `MUTED_FOREVER` and `byDmActivity` (`docs/dms.md` §3.4). 2.0.0 removed the default provider: `ctx.ai.complete`, `ctx.ai.effective`, `AiSettings.defaultProvider`, `aiRuns.verb`/`settingsTab` and the test host's `ai.defaultProvider`; it added the kit's `ProviderSelect` (a feature's provider pick) and `settingFields[].shared`.
- **Not yet supported:** packages that load files relative to themselves, and native modules.

### The build

`buildInstalledPlugin({ pluginDir, outDir, appVersion, repoRoot? })` (`src/main/pluginBuild/`, relative imports only, so main can import it) writes into an empty `outDir` and returns the manifest; plugin.json is written last, so a failed build leaves no loadable folder.

- **Two Vite builds.** Node: shared, core and main, as SSR output with every package bundled and `node:` built-ins kept as imports. Browser: shared and renderer (and a page's entry, `page.js`), through vite-plugin-solid. Entries are `<side>.js` with their exports kept exactly (`preserveEntrySignatures: 'strict'`); shared code goes to `chunks/`, stylesheets and other assets to `browser/assets/`. `node/package.json` marks node files as ES modules whatever package.json sits above the install. Unminified.
- **Shims.** Each host module resolves to a virtual module that reads `globalThis[HOST_MODULES_KEY][id]` (throwing, naming it, when the host published none) and whose named exports are synthetic (rollup's `syntheticNamedExports`), so every import reads the host's namespace. `hostImports` is every name each bundled module's import declarations take from a host module, read from its AST: it can list a name tree-shaking later drops. Externals were rejected: rollup renders an absolute external relative to the input folder, wrong when the output sits elsewhere (on another drive on Windows).
- **Refused, naming the file:** a page that isn't one HTML file with one `<script type="module" src="./…">`, a `</head>` and no relative URL (see Pages); CSS breaking §14; host internals (`@shared`, `@core`, `@main`, `@/`, `electron`); the other platform's host module, or a host package's module the host doesn't provide (`@plugin-sdk/core/testing`, `solid-js/html`); `import *`, `export *` or a dynamic import of a host module (the host couldn't check the names); Node built-ins in browser code; relative imports leaving the plugin folder.
- **Descriptor.** With `repoRoot` (a ChattyPop checkout; the release script), the shared descriptor is evaluated from source with the checkout's SDK and `checkBundled` runs on it with the anchor catalog of `anchorFolders` (the scripts pass its repo's other plugin folders, `scripts/anchorFolders.ts`; a folder holding its own id is left out); the theme's look tokens join the style check. Without it (the app's source installs), the descriptor is imported from the built `node/shared.js` through the host modules the process published; the start runs the descriptor checks, and the style check knows only the plugin's own look declarations, so setting a custom property the theme's look reads passes. plugin.json's id, name, version and description come from the descriptor.
- **`__APP_VERSION__`** is `appVersion`, the version of the ChattyPop that built it, fixed into the build (Codex reports it as its client version). A plugin rebuilt by a newer app reads the newer one.

### Releasing

Plugins release themselves. A plugin's version is the `version` string literal in its `definePlugin` manifest (`shared/index.ts`, inline or a same-file `const` object); nobody edits it. `pnpm plugin:release-changed <pluginsRepoDir> --repo <owner/name> [--dry-run] [--only id,id] [--sdk-rebuild]` (`scripts/pluginReleaseChanged.ts`, run by Vite's module runner through `scripts/runTs.mjs`) runs in a clone of a plugin repo: from CI on every push to its `main` (below), or by hand. Through `git` and `gh`:

1. **Preflight**, before any write: `origin` is `--repo`, the clone is clean and on `main`, and after `git fetch origin main --tags` its HEAD is `origin/main` (else "pull first").
2. **State** (`scripts/pluginReleaseState.ts`), per plugin, from `origin/main`: its literal L against N, the newest release its `marketplace.json` lists. N's recorded tag must exist, be on `main` and hold that id and N. L == N is *settled*: *changed* when `git diff <N's tag> origin/main -- plugins/<id>` differs (content, so a merge-only edit counts). Its new version raises N once per non-merge commit in that range touching the folder, oldest first, as `appVersion` counts: a commit matching the app's `FEATURE_SUBJECT` (`feat`, scoped or `!`) raises the minor and resets the patch, any other the patch (1.2.0 + fix, feat, fix → 1.3.1); a change made only in a merge is one patch. One release per run, at that version. A plugin is *pending* while a release-intent commit names a version of it above N (any, when unlisted): the lowest such version is released at that commit whatever lands on `main` later, even one a hand-raised literal passed over. Otherwise L > N (or unlisted) is *unstamped* (a new plugin, or a version raised by hand) and gets an intent commit at L. L < N or a bad tag marks it broken: reported, nothing done for it.
3. **Pending first.** Each is published (below). Their listings are commits on `main`, so the clone then fetches, fast-forwards and reads the state again.
4. **Stamp.** Each changed or unstamped plugin (with `--sdk-rebuild`, also each settled one whose newest listed `sdk` isn't `PLUGIN_SDK_VERSION`; a rebuilt one lists the new SDK, so reruns don't bump twice) has its npm packages installed (`npm ci`) and `checkPlugin` run; any failure stops the run before writing. Its version literal is replaced in place (`stampVersion`, `scripts/pluginScan/manifest.ts`), each stamped descriptor is evaluated with `sourceDescriptor`, and one commit `chore(release): <id>-v<x>, …` holding only the stamped files (empty for a first release at its literal) is pushed. A rejected push undoes that local commit and fails the run: nothing is pending, and the push that won has its own run. Each is then published at that commit.
5. Exits non-zero naming every plugin not released. `--dry-run` prints the state and the planned versions and still installs and checks, but stamps, pushes and publishes nothing.

**Publishing** is `ensureReleased` (`scripts/pluginRelease.ts`): it converges from whatever an interrupted run left, deleting or replacing nothing but a failed upload's empty placeholder (an asset not in GitHub's `uploaded` state), which it removes and uploads again. The tag, when present, must be at the target (a draft without one must target it); no release → build the asset and `gh release create` (`--verify-tag` on an existing tag); a release without the asset → build it and `gh release upload` (no `--clobber`); a draft → publish it. Then it downloads the published asset, hashes it and reads its plugin.json (id, version, and the `sdk` the listing records, so an old asset keeps its true SDK), and adds the version to `marketplace.json` over the contents API at the read sha (newest first; name and description follow the newest release; every other field kept), re-reading on a 409 up to `INDEX_WRITE_ATTEMPTS` times. A version already listed is a no-op when its tag and sha256 match, else an error. Any failed write throws.

**The asset** (`scripts/pluginAsset.ts`) is built only when the release lacks it: a temporary `git worktree` of the plugin repo at the target (siblings at that commit, for anchors), the plugin's packages installed, `checkPlugin`, then `buildInstalledPlugin` against this checkout, the build folder's contents packed as `<id>-<version>.tar.gz` with plugin.json at the archive root. The release notes record the target, the host's version and commit, its installed `@cujuju/*` package versions and the SDK. A missing asset (only after an interrupted run) is built with today's host; the listing's `sdk` comes from the asset actually published either way.

**CI.** `ChattyPop-Plugins-Public/.github/workflows/release-plugins.yml` runs on every push to `main` (not only `plugins/**`: when a run's intent push loses a race, the winning push's run releases its changes), on `workflow_dispatch`, and as a reusable workflow other plugin repos' `release-plugins.yml` call, with inputs `only`, `sdk_rebuild` and `dry_run`. One run at a time (`concurrency: plugin-release`, queued). On `windows-latest` it checks out ChattyPop (full history, for `appVersion`, with the `CHATTYPOP_READ_TOKEN` secret), installs Node 24 and the host's pinned pnpm, installs the host (its `@cujuju/*` packages from npm), checks out the plugin repo and moves to the current `origin/main` (a queued run starts from the latest `main`, not its trigger), then runs the script as `github-actions[bot]` with the run's `GITHUB_TOKEN`. Pushes made with that token start no runs, so the release's own commits don't loop. Owner setup, once: a fine-grained read-only (Contents) token for ChattyPop as `CHATTYPOP_READ_TOKEN` in each plugin repo; Actions allowed to push to `main` if it is protected; other plugin repos allowed to use the reusable workflow; then a `dry_run` dispatch on each repo and a real one. Until the host has CI, a `PLUGIN_SDK_VERSION` change needs an `sdk_rebuild` dispatch.

### Checking a plugin outside the checkout

`pnpm plugin:check <pluginDir>` (`scripts/pluginCheck.ts`) checks a plugin folder in a marketplace repo against this checkout. Steps run in order; the first failure prints `plugin:check failed at <step>` and exits non-zero.

1. **typecheck.** One tsc run per side, with a tsconfig generated in a temp folder that extends `tsconfig.plugin.json`. Node covers `shared/`, `core/`, `main/`, `tests/` and `**/*.test.ts`. Browser covers `shared/`, `renderer/` and `page/` (not `page/public/`, served as is). Each side takes `lib`, `types` and ambient `.d.ts` files from `tsconfig.node.json` or `tsconfig.web.json` (read with `tsc --showConfig`). `tsconfig.plugin.json` maps every alias those two configs map (a test keeps them equal), the host test kit, and the packages the host provides, `solid-js` and `vitest`, to this checkout. A plugin's own packages come from its folder's `node_modules`, as a source install installs them.
2. **styles.** `checkStyles` (§14) with this checkout's root, so the theme's look tokens are known.
3. **scan.** `scanPlugin` (`scripts/pluginScan/`) reads the plugin's source as the app's tests read `src/plugins` before plugins left, and lists every violation as `file:line: message`. Source is every script and stylesheet in the folder but `tests/`, `*.test.*`, `node_modules/` and `page/public/` (static files, copied as they are). The folder name is the plugin id. Rules:
   - **Imports** only the SDK entries and Solid modules the host provides (`HOST_MODULES`), Node built-ins, the folder's package.json `dependencies`, and its own files. Type-only imports count. `@plugin-sdk/renderer/shell` only when the descriptor declares `phone.transport` (the descriptor is evaluated only then).
   - **Page.** Nothing outside `page/` imports `page/`.
   - **Tables.** No literal `p_<id>_` prefix: names come from `pluginTable` or `ctx.storage`.
   - **App** only through the contexts: no `createRequire`, `globalThis` or `.chattypop` bridge.
   - **Warnings** (`scanWarnings`), logged without failing: a Node network module (`http`, `https`, `net`, `tls`, `dgram`) or a web request (global `fetch`, bare, `window.` or `self.`; `new XMLHttpRequest`/`WebSocket`/`EventSource`; `sendBeacon`), which the developer may choose but which skips `ctx.net`'s declared hosts (in the renderer, its CSP refuses other origins); and a string naming Discord's API (`/api` on a Discord host) or gateway/voice (`gateway*.discord.gg`, `discord.media`, `ws(s)://`), which only the embedded client reaches (law 4). Jump links and media URLs aren't warned of.
   - **Tests stay tests.** Source never imports `tests/` or a `*.test.*` file: the scan skips them.
   - **Read from the syntax tree** (`@babel/parser`): imports of every form (statements, `import()`, a type's `import()`, `require()`; a computed specifier is refused) and the globals above, never in comments or strings. A lint, not a sandbox: a plugin runs with the app's full rights, so trust comes from its repo.
   - **SQL.** Every SQL literal is checked as in §3's archive views: archive views read, own tables (constants from `pluginTable`, imported ones included) written, `archive_all_*` only from files in `scripts/pluginScan/allReaders.ts` or the repo's `all-readers.json`, no privacy predicates.
   - **Styles.** Each `user-select` has a `-webkit-user-select` of the same value (Safari on the phone).
   - **Version.** `shared/index.ts` has one `definePlugin` call whose manifest (inline, or a same-file top-level `const` object) has string-literal `id` and `version`, so a release can stamp it.
4. **build.** `buildInstalledPlugin` into a temp folder with `repoRoot`, as a release asset builds. It refuses everything the release refuses (host internals, descriptor checks) and builds a `page/` as the release does. The typecheck can't catch host internals: the SDK imports `@shared`/`@core`/`@main` itself, so those aliases resolve. Its anchors resolve through its repo's other plugin folders; a stamped anchor on a plugin not among them is accepted as absent (§6).
5. **tests.** The folder's `**/*.test.ts` run in-process on this checkout's vitest config (`testConfig()`): its aliases, `__APP_VERSION__` and the run's temp folder (`tests/globalSetup.ts`), with the registry built from the folder alone (passed to `testConfig` as its parent folder, selected by folder name), as a development run loads it, so the registry and the tests share one copy of the plugin. A package the plugin's folder doesn't have (electron, solid-js) resolves from this checkout, as the host provides it, so the tests and the host's modules share one copy and a `vi.mock` of it reaches both. A mock factory must load its module through Vite, not Node's `require` (which looks from the plugin's folder): Solid's client build, for example, is `vi.mock('solid-js', () => { const client = 'solid-js/dist/solid.js'; return import(client); })`, the variable keeping the typecheck off a path without declarations.

**Host test kit** (`@chattypop/host-testing`, `tests/hostTesting/`). It only re-exports. The files stay in `tests/`, so a test moved out of this checkout changes only its import paths. Relative imports of the plugin's own files stay relative. Host imports go through the SDK (`@plugin-sdk/*` and its testing entries, §15) or the kit:

- `tests/helpers.ts`, `fakeJev` (a Jev stand-in), `hostRules` (the host's rule services with no plugin's kinds: `hostRuleStack`, `ruleInput`, `runsOf`) and `pluginReadHarness`. The kit reaches no plugin's code (`tests/pluginCheck.test.ts`), so it loads once plugins leave this checkout; a plugin's own harness (its activation over the host, as `alertsHarness` was) lives in the plugin's repo. The helpers listed in `tests/hostTesting/files.ts` are also reachable by name, `@chattypop/host-testing/<file>` (e.g. `@chattypop/host-testing/archiveViewsFixture`), for one that needs a module mocked before it loads; the same test walks each. Host internals a test drives (the plugin host, rule engine, archive) come through the same aliases the host's tests use (`@core/*`, `@main/*`, `@shared/*`): test files only, since the build refuses them in plugin code.
- `@chattypop/host-testing/fixtureProviders`: stand-ins for the provider plugins (Claude, ChatGPT, Ollama, OpenRouter, declared as theirs are). Only the plugin under check is in a check's registry, so a test whose plugin asks providers adds them: `vi.mock('virtual:bundled-plugins/shared', async (build) => (await import('@chattypop/host-testing/fixtureProviders')).withFixtureProviders(build))`.
- The test-only host API: `claimRun`, `loadRule`, `recordOutcome` and `ruleRows` (`src/core/rules/ruleStore.ts`), `newRuleAction` (`@shared/ruleSpec`), and `Database` (`better-sqlite3-multiple-ciphers`, for a database an earlier version left).

The app holds no plugins: each plugin's harness and tests live in its repo. The host's own tests use the rule probe (`tests/pluginRuleProbe.ts`, through `tests/ruleHarness.ts`), the read probe (`pluginReadHarness`) and fixture descriptors; the kit reaches only files in this checkout (`tests/pluginCheck.test.ts`).

**Editor.** A plugin repo cloned beside a ChattyPop checkout points VS Code at it with one `tsconfig.json` at the repo root. If the checkout sits elsewhere, change the relative path.

```json
{
  "extends": "../ChattyPop/tsconfig.plugin.json",
  "include": ["plugins/**/*", "../ChattyPop/src/**/*.d.ts"],
  "exclude": ["**/node_modules/**"]
}
```

This config puts node and DOM types in one project, so it is looser than the check. `tsc -p` on it also reports one false error in a host file: `structuredClone` is typed differently in DOM and Node. That error is not in the plugin's files, and `plugin:check` checks each side alone.

### Start

Node can't unload a module, so installs, updates and removals apply at the next start; on and off stay live.

1. **Main, before anything else.** Its entry (`src/main/index.ts`) is a boot module that, synchronously and before `ready`, sets the app identity and profile, registers schemes, sets Chromium switches, applies staged changes (`.held` settled, `.removed`, then `.staged` swapped in through `.trash`; `staged.ts`), and decides each installed plugin in id order (`boot.ts`, checks in `src/shared/installedCheck.ts`). Its manifest comes first, before any of its code runs: format, id matching its folder, no clash with a bundled id, `sdkMismatch`, `missingHostImports` over the node tiers. Then its `node/shared.js` loads synchronously (`require` of an ES module, after publishing `@plugin-sdk/shared`), its descriptor's id must match, and `checkBundled` runs over the build's descriptors, those accepted so far and this one, with the anchor catalog merged. It sets `INSTALLED_ENV` (the `InstalledStart`) and then imports the app (`src/main/app.ts`, its own build entry so it sits beside `core.js`). A refused plugin never loads further and shows in Settings → Plugins with its reason; a throw refuses that plugin alone, and a failure of the whole step starts with none. Dot folders (`.staged`, `.held`, `.removed`, `.trash`, the installer's `.incoming`) are never plugins.
   - **Staging is crash-safe.** Each step is a rename or delete that the next doesn't depend on, so a crash leaves a state the next start completes: an old copy already in `.trash` with its `.staged` copy waiting, a `.removed` marker whose folder is gone, or a staged copy in `.held/<id>` that a newer one was replacing (put back when no replacement is staged, else deleted). A step that fails (a file held open) is logged and retried at the next start, and holds back that plugin's later steps, so a marker that couldn't be deleted can't remove the copy installed after it; a staged update whose final rename fails leaves the plugin out for that run.
   - **`@plugin-sdk/core` and `@plugin-sdk/main`** can't load in the boot: their imports reach the registry. Their export names are read from source at build time (`virtual:installed-plugins/host-exports`: types erased, `export *` refused since its names aren't listed), and a test checks them against the modules' run-time exports.
2. **Registries.** `@shared/bundledPlugins` lists the build's descriptors then the accepted ones (`virtual:installed-plugins/shared`), with installed plugins' anchors merged into the catalog, so every lookup over it (rule kinds, audiences, phone calls, notices, anchors) sees installed plugins with no change. Core and main registries append accepted `node/core.js` and `node/main.js` after publishing `@plugin-sdk/shared` and `@plugin-sdk/core` or `@plugin-sdk/main`; a side that throws or isn't its plugin's is left out and exported as `failed`. `require` shares the module cache with `import`, so every process loads each file once and the boot's descriptors are the registry's. The generated code is per platform (`bundledPlugins(root, 'node' | 'browser')`).
3. **Core** inherits `INSTALLED_ENV` (`CoreClient` forks with main's environment) and loads the accepted plugins the same way, without deciding again. Its plugin host lists each plugin's `origin` (`bundled`, `installed`, `folder`; `bundled` stays true for any descriptor plugin), the refused ones as `error` with their reason, and an accepted one whose module failed in core as `error`. Data folders and adoption treat installed ids as bundled ones.
4. **Windows and the phone page** read the accepted list from main (`chattypop-installed://` on the desktop, `/installed/` from the phone transport's server on the phone) and load `browser/` modules with top-level await in two steps: the shared registry publishes `@plugin-sdk/shared` and imports each `shared.js`; the renderer registry publishes the renderer tiers and Solid, adds each plugin's stylesheets and imports each `renderer.js`.

The shared SDK tier, `bundledCheck`, `installedCheck` and everything the boot runs before importing the app must never load the plugin registry, or the boot would read it before the installed list exists (`tests/installedPlugins.test.ts`).

Limits: `INSTALLED_ENV` carries each accepted manifest, `hostImports` included, and Windows caps a variable at 32,767 characters. Node reads a `.js` file with ES syntax as a module by syntax detection; a `package.json` declaring `"type": "commonjs"` above the profile would break that.

### Windows and the phone page

- **Serving** (`src/main/plugins/installedFiles.ts`, `src/shared/installedBrowser.ts`). One handler serves both: `index.json` (the accepted manifests in load order; a dot, so never a plugin id) and `<id>/<path>`, files under that plugin's `browser/` only (resolved and real paths contained; `INSTALLED_CONTENT_TYPES`: `.js .css .map .json .webmanifest .svg .png .webp`; CORS `*`; `no-store`, so a page loaded after a restart gets the new files). Desktop: the privileged scheme `chattypop-installed:` (in the renderer CSP's script, style, img and connect sources). Phone: `ctx.pages` answers `/installed/` itself, in development too, behind the phone transport's pairing cookie; its service worker has no fetch handler. Main reads the list from `INSTALLED_ENV`; a malformed value or entry is logged (`installed-plugins-unreadable`) and left out.
- **Loading** (`src/renderer/src/plugins/installed{Loader,Shared,Renderers}.ts`). The browser registries (`bundledPlugins(root, 'browser')`) list the build's entries, then `...await` their loader. The desktop's windows (the preload's) use the scheme, a page without it `/installed/`. The shared loader loads only `@plugin-sdk/shared`: a renderer tier reads the shared registry it completes (`tests/rendererBoundary.test.ts`). Each plugin's `hostImports` for the published modules are checked before its module loads. Stylesheets are `<link>`s after the page's own, awaited before its `renderer.js`, so nothing renders unstyled.
- **Order.** Top-level await lets a page entry loaded beside the registry, not through it, run first; `startPage` renders once the registry installs (`rendererPluginsInstalled`). `main.tsx` imports the registry, so it waits.
- **Failure.** A plugin whose index entry, module, default export (another id), host import, stylesheet or slot views fail is left out of that window with a console error naming it, and its stylesheets are removed; the window keeps working. The plugins whose shared side loaded are then kept as main's start keeps them (`acceptInstalled` in `installedCheck.ts`), and one anchored on a plugin that failed here is kept, its items placed as if that plugin were not installed; core and main do the same over their node shared modules. Its slot views are checked by the loader, so the registry's no-renderer check skips installed plugins. Residuals: core and main still run it and Settings → Plugins shows it on; a failed `shared.js` leaves the window without its descriptor (as a plugin not in this build), a failed `renderer.js` keeps the descriptor without views.

### Pages

An installed plugin's `page/` is served like a bundled one's (§3, plugin page): `ctx.pages` answers `/<id>.html` and the page's public files, so the plugin asks for the same URL either way.

- **Build** (`src/main/pluginBuild/page.ts`). `page/index.html` must hold exactly one script, `<script type="module" src="./<entry>">`, a `</head>`, and no relative `src`/`href` (it is served at `/<id>.html`, not from its folder: link public files by absolute path). The entry builds with the browser sides as `browser/page.js`, sharing their chunks, so the phone has one instance of each module. The HTML is written without its script as `browser/page.html`; `page/public/**` (files only) is copied to `browser/public/`. `browser.page` lists `html`, `entry`, `styles` (the CSS its entry reaches, statically or dynamically) and `public`; `browser.styles` keeps every stylesheet but those only the page imports. Absent `browser.page` means no page, so `INSTALLED_FORMAT` stays 1 and an older host ignores the field. `parseInstalledManifest` keeps each path under `browser/`, public files under `browser/public/` with a type `/installed/` serves (`INSTALLED_CONTENT_TYPES`) and none under `browser/public/installed/` (shadowed); `manifestFiles` lists every named file, and installs refuse a build lacking one.
- **Order.** The host modules exist only once the registry has run (top-level await), and a page's own module script would run beside it, before then, so its shims would throw. The host loads the entry instead: the renderer build always emits `installed-page.html` (`INSTALLED_PAGE_SHELL`, built by `pagesPlugin`), whose head holds `src/renderer/src/plugins/installedPage.ts`: the page bootstrap (theme, registry), then `import()` of the URL in the page's `chattypop-page-entry` meta. The bridge therefore installs after the registry, as in a production build of a bundled page.
- **Serving** (`installedFiles` `page`/`publicFile`, `rendererPages`). `/<id>.html` is `page.html` with, before its `</head>` (after its own metas, its CSP first): the shell's head (read from the build, or fetched from the dev server), a `<link>` per page stylesheet and the entry meta, all under `/installed/<id>/`. Same reply as a bundled page: `text/html; charset=utf-8` and its length; the phone transport adds its headers. Public files are served at their path below `browser/public/`, the first plugin in load order winning. Both are answered before the build's files and the dev server (a bundled plugin can't share an installed id). A page HTML missing or outside `browser/` answers its status (404, 403); `/installed/` never serves `.html`; a build without the shell answers 500 (dev server down: 502).
- **Residuals.** A page's host imports are checked by the window's loader with the plugin's renderer step (one `hostImports` per plugin); a missing name leaves the plugin out with a console error, but the page entry still loads and fails where it uses the name. A plugin's public file can shadow a host build file of the same path.

### Marketplaces

A marketplace is a GitHub repo with `marketplace.json` (`MarketplaceIndex`) on its default branch: a built-in one, or one the owner adds by hand. Main does all network and file work; windows call `RendererApi.marketplace`.

- **Built in.** `BUILT_IN_MARKETPLACES` (`Cujuju/ChattyPop-Plugins-Public`) is listed first in every profile, never stored in `marketplaces.json`, and needs no token. It can't be removed: `remove` and `setToken` refuse it, and `add` refuses it as always listed (one added before it was built in shows once, as built in). Its listing carries `builtIn: true`; Settings → Plugins → Marketplaces marks it "Built in" and shows no token or Remove buttons.

- **Access.** GitHub's REST API only. A private repo's token is fine-grained and read-only, stored with `safeStorage` in the profile's secrets, sent only to `api.github.com`, and never logged. Downloads follow redirects by hand, without the token.
- **Prebuilt install.** Download the release asset, check its sha256 against the index, unpack the `.tar.gz` (the `tar` package, refusing links and paths outside the folder) into a temporary folder, check `plugin.json`, then move it to `.staged/<id>`.
- **Source install.** Resolve the branch's latest commit, download the repo's tarball at that commit, install the plugin folder's runtime packages (its `package.json` `dependencies`) with `npm install --omit=dev --ignore-scripts` (`src/main/marketplace/npm.ts`, shared with releases; npm found only in PATH's absolute folders and run without a shell, on Windows as `npm-cli.js` on the node beside it, so nothing in the plugin's folder can stand in for it), build it with the same build function (`src/main/marketplace/sourceBuild.ts`, loaded on demand), then stage as above. Updates compare the installed commit with the branch's latest. Needs npm on PATH and ChattyPop run from its checkout (Vite and the Solid plugin are development packages, kept out of main's bundle); otherwise it refuses, naming what is missing. Every listed plugin can install from source: its `source: { path, branch }` in `marketplace.json` when the entry has one, else its `plugins/<id>` folder (`MARKETPLACE_PLUGINS_DIR`) on the repo's default branch, which the client reads with the index (`GitHub.index`).
- **Local install** (development): a built folder or `.tar.gz` on this PC, staged the same way.
- **Remove** stages removal; data (tables, preferences, data folder) stays. **Cancel** drops a pending change (staged copy or removal marker).
- **Versions.** Release and SDK versions are x.y.z (`VERSION_PATTERN`), ordered by one `compareVersions` (`src/shared/installedPlugins.ts`). An installed version that isn't x.y.z (a local `1.0.0-beta`) has no order against a release, so the store offers a release over it as a switch, never as an update. `parseMarketplaceIndex` refuses a version listed twice and sorts releases newest first, so `releases[0]` is the newest whatever order the file has.
- **Client** (`src/main/marketplace/`). Repos in the profile's `marketplaces.json`; each token in secret `marketplace.<owner>+<name>.token`. `add` reads the index before saving. Listings are cached in memory, fetched on add, `setToken`, install and refresh (none after a start until refresh); a failed fetch is the listing's `error`. The token goes only on a request's first hop and only to `api.github.com`; redirects (`redirect: 'manual'`, at most `MAX_REDIRECTS`, HTTPS only) go without it. Timeouts and a download size cap are named constants in `github.ts`. A release's `sdk` is checked before downloading. Work happens in `installed-plugins/.incoming/` (cleared when main starts, each work folder deleted after its install; a delete that fails is logged, never failing the start or the install); every build is checked like the loader does (manifest, index id and version, `sdkMismatch`, every entry file present) before `source.json` is written and it is renamed to `.staged/<id>`, replacing an older staged copy and clearing a `.removed` marker. Archives may hold only files and folders: links, devices, absolute paths and `..` refuse the whole install, so a repo with a symlink anywhere can't install from source. A source build gets `<tarball top>/<source.path>` and an empty out folder. Mutations queue per plugin id (install, uninstall, cancel; a local install from its staging step, once its id is known). A failed swap into `.staged/<id>` puts the older staged copy back; it waits in `.held/<id>` during the swap, so a crash mid-swap loses neither.
- **Publishing** (`pnpm plugin:release-changed`, Releasing above): CI on each plugin repo's `main` stamps changed plugins' versions in a pushed release-intent commit, releases `<id>-v<version>` there with its asset (never replacing one) and lists it in `marketplace.json`; an interrupted release finishes on the next run.
- **Install history** (`src/main/marketplace/history.ts`, the profile's `plugin-history.json`, `PluginHistory` in `state()`). Per plugin id: the repo it was last staged from (null for a local build) and whether its removal was asked for since. Staging records the repo and clears the flag; `uninstall` sets it (taking the repo from `source.json` for a copy installed before the history); `cancel` puts back the entry from before the staged changes (kept beside them as `beforeStaged`), so a cancelled reinstall stays removed and a cancelled update from another repo keeps the running copy's origin. It outlives the plugin's folder, for restore. An unreadable file reads as empty.

### Restore

A profile can hold a plugin's data without the plugin: it was bundled before plugins left the app, or the profile and archive were copied to a ChattyPop without it. Restore offers to install it again.

- **Footprints** (`src/core/plugins/footprints.ts`, core method `absentPlugins`, renderer-callable). Each kind alone lists a plugin: its tables (`p_<id>_<name>`), preferences (`plugin.<id>.*` settings), data folder (`plugin-data/<id>`), rule parts of its kinds (`ruleKindPlugin`) or managed rules (`rules.builtin` `<id>.<key>`), and its on/off state (`plugins.disabled`, and `plugins.continuity`, which keeps an entry for a plugin absent from the build: its old session never counts as resumed). Every plugin core lists (bundled, installed, refused, folder) is left out; the method waits for the plugins folder to load. A table name can't say where the id ends (`p_a_b_c`: `a` with table `b_c`, or `a-b` with `c`), so a table fitting several ids goes to the longest that is loaded (dropped) or has other data; otherwise it is listed with every candidate (`AbsentPlugin.ids`). Residual: a plugin whose only data is such a table, while a plugin with the shorter id is loaded, is not listed.
- **Matching** (`restoreItems` in `src/shared/pluginRestore.ts`, pure). Windows first refresh listings not read since the start, then match each absent plugin to the first marketplace listing it (installable first; candidate ids longest first), only its origin marketplace when that is known, so another repo's same id never stands in. It installs the newest release whose SDK runs here, else from source; otherwise the row says why. A plugin no marketplace lists says "Needs marketplace <repo>" when its origin repo isn't added (or couldn't be read), else "Not found in your marketplaces". The origin (`originRepo`) is the install history's repo, else, for a plugin the app bundled before plugins left the app, the repo it moved to (`MOVED_PLUGINS`). The notice then shows one form per such repo: its token, and Add marketplace (Save token when it is added but unreadable; none for the built-in one, which is public). Left out: plugins installed or staged now, ones whose removal the history records, and dismissed ones.
- **Offer.** Settings → Plugins' notice slot shows "N plugins you used aren't installed" above the restart notice, each with Install and Dismiss, and Install all. Installing is the marketplace's `install`; the restart notice then applies it. Dismissal and the start prompt are remembered per plugin id in the archive's `plugins.restore` setting (`{ dismissed, prompted }`). At start the main window opens Settings → Plugins once for offers the start hasn't shown before. No generic one-time-notice mechanism existed, so the prompt reuses `openSettingsAt` and the notice slot.
