# Discord bookmarks and reminders

Discord owns saved messages. A bookmark has no `due_at`; setting `due_at` converts it to a reminder. Completing/removing either deletes the same saved record. ChattyPop exposes this account state through the existing embedded client's transport.

## Interfaces

- `savedMessages(refresh?: boolean): SavedIndex` returns the main-owned cached reminders, bookmark identities and privacy-visible `writableChannelIds`, loading once on first use. Explicit Refresh passes `true`. The index carries an opaque, non-secret `session` and a revision monotonic within that session. Older `{results}` responses also supply the complete bookmark list.
- `savedBookmarks({session, pageEpoch?, before?, refresh?}): SavedBookmarkPage` returns a cached page or loads 25 bookmarks ordered by save time. Indexes, pages and change events carry a main-owned `pageEpoch`; stores discard deeper pages/cursors when it changes. `before` is the last native `saved_at`, including microsecond precision, not a message snowflake. Hidden rows do not change the native cursor. Refresh begins at the first page.
- `saveMessage({session, revision, channelId, messageId, source, dueAt?}): void` sends the native PUT. `dueAt` is omitted for bookmarks and a validated future ISO timestamp for reminders. Sources are restricted to `context_menu` and `for_later_list`. Revision fences changes made elsewhere while the menu/dialog is open or a retry waits.
- `removeSavedMessage({session, revision, channelId, messageId}): void` sends the native DELETE, including Mark complete.
- `saved-messages-changed {session: string|null, revision, pageEpoch, reset}` invalidates views without broadcasting message content. Page refreshes change the epoch without cancelling revision-bound edits. The existing passive gateway tap observes creates/deletes. READY, authentication invalidation/replacement, and privacy changes fence old work.
- Core-only `filterSavedMessages(items, bookmarkIds)`, `savedTargetVisible(target)` and `savedWritableChannels(accountId)` use the archive's privacy and permission rules. Main intersects permission facts with the current gateway directory and private-thread visibility/membership. Unknown bookmark identities are omitted from the renderer's index until a visible row is loaded. No new renderer/plugin core capability grants access to these filters.

Normalized rows contain channel/message/guild identity, save/due timestamps, plain text author/channel/message summaries, and whether the original message is available. They do not carry credentials, raw native message objects, media URLs or arbitrary request options. Saved content is held in memory; Discord remains the durable store.

## Request protections

Use `DiscordApi.prompt` through the existing `postingClient` wrapper. Reads and user writes remain in its single queue, route/global rate limits, captured session headers, API-origin boundary and client-shape checks. No new network stack, gateway connection, polling loop, fabricated headers, webpack execution, entitlement spoofing, or posting-lock exemption. PUT/DELETE use `once` semantics: preserve rate-limit retries but do not retry ambiguous server failures. Validate identifiers, source, session and time in main; repeat the account/privacy/time checks immediately before each attempt and reject stale account responses afterward.

New saves additionally require current read-history access (an owned open DM, or a visible live guild channel/public thread; private threads also need native visibility/membership). The native context menu explicitly permits existing saves to be edited/completed after access is lost, and ChattyPop preserves that distinction. List-source edits and removal require an existing saved identity linked to its channel, through a normalized native row or a privacy-visible archived original. Core rejects archived message/channel mismatches. Permission events are coalesced and only actual writable-set changes invalidate edits; unrelated members cannot cancel a draft. Each attempt still rechecks current permission. Bookmark pages require a loaded raw index and a cursor returned by a cached page with `hasMore`; an empty raw index or historical full list causes no page request. Saved reads disable automatic 5xx retries while retaining the shared queue and 429 handling; a refusal waits for explicit retry. Explicit index/first-page retries are capped at one per minute each, limiting repeated refusal traffic while allowing an immediate first retry.

Authentication fencing adds an opaque generation to HeaderCapture; it changes on invalidation or replacement of an existing token, never on routine header recapture. The existing passive tap supplies socket provenance. IDENTIFY's observed credential is compared in memory with the actual captured REST authorization; it never supplies REST headers. Only READY on that identified socket plus matching capture authorizes a scope. Either capture/READY order works. Late frames from older sockets cannot bind an account. Same-credential native RESUME can retain proven identity. A revoked credential clears that proof and requires fresh native IDENTIFY/READY; reopening/reloading the live client is the recovery path. Replacement cannot authorize requests until its capture matches the currently proven gateway credential.

Privacy filtering occurs in core before any content reaches a desktop, remote desktop or phone. Privacy events immediately clear visible saved state and dialogs. Older asynchronous responses cannot repopulate it. Actions from stale menus carry their original session and cannot act on another account.

## View behavior

Add an optional Bookmarks panel with Bookmarks and Reminders tabs, Refresh, Load more, loading/error/empty states, plain text summaries and unavailable-message placeholders. Open message navigates to an archived original; an unarchived original produces an instruction to use the live Discord client. Reminders sort by due time and show overdue state. Actions include remove, mark complete, edit reminder and convert bookmark to reminder. Existing posting locks govern all mutations.

The message context menu gets Bookmark/Remove bookmark, Remind me presets (30 minutes, 1 hour, 4 hours, 9am today/tomorrow, Monday 9am), custom local date/time and reminder edit/complete. An uninitialized menu offers opening the list and, only while posting is unlocked, initializes the index for the next menu opening. An already-open menu is never rearranged asynchronously. Custom time uses local calendar fields and round-trip validation to reject nonexistent DST times. Presets use local calendar arithmetic, not fixed 24-hour offsets.

Stores own RPC calls and account/revision fencing. Panels read stores only. Main applies native create/delete events and successful PUT responses to its shared memory cache; duplicate PUT echoes do not refetch. Events received during a read are replayed onto its result, so they neither trigger another network read nor latch a local conflict. Message edits do not refetch; deletions retain summaries and mark original availability locally. Concurrent windows share each in-flight read. Content-free events update mounted panels from that cache, or only the cached index when unmounted. Index-only updates filter retained rows against the current bookmark identities. Joining an index-only menu read with a panel read upgrades it to load bookmarks without another index GET. Account/privacy resets clear message menus/dialogs and require a new user read. No periodic Discord queries. Failed reads are latched across views until explicit Refresh, which clears all page caches/failures, broadcasts the new page epoch and fences older requests. Index failures also survive same-account re-identification; changing the proven account clears that latch. Malformed native saved events fail closed until Refresh. Same-scope refresh failures retain prior visible content while disabling stale actions. A main-process restart can be adopted even if its new session has a lower revision. Native modal close events cannot dismiss an already reopened dialog.

Discord's embedded client remains the sole reminder notification owner. Its inspected code schedules desktop reminders locally and respects its own notification settings. ChattyPop's badge counts overdue reminders already loaded on demand; there is no startup read or second notification timer. Unverified: notification delivery while the desktop app is closed and mobile push behavior; no such guarantee is made. Native notification delivery must be checked in runtime QA when an account with available saved messages can be used.

## Evidence and alternatives

Verified from retained modules 216623 (actions), 85109 (store), 343509 (notification scheduler), 595528 (gateway translation), and cached context/preset chunks in the October 9, 2026 Discord web build `web.843cc7edc28c426c.js`. PUT `/users/@me/saved-messages/{channel}/{message}` with `{due_at?,source}` in native field order; DELETE the same path; GET `/users/@me/saved-messages?bookmark_ids=true`; GET `/users/@me/saved-messages/bookmarks?before=<saved_at>&limit=25` (omit before for the first page). Historical full-list shape is supported by decoding, without speculative fallback requests. Limit code 30074 is handled as a server refusal; observed client caps are not enforced as server facts.

The retained research chunk `2acd694fcc6e6223.js` contains the source enum literals and reminder editing with `FOR_LATER_LIST` (SHA-256 `64493f8f046df271ee4907c4d681667d622978993d69139e02a1426f4fee088d`); chunk `0b8d8a40b7b82fdb.js` supplies `CONTEXT_MENU` (SHA-256 `d638a1c592d64a1a964d4a156750562fc4de1575fb79b3b02429e1215b927005`). These are static reads, with no module execution or native-client modification.

Primary public documentation: [Discord Message Bookmarks and Reminders](https://support.discord.com/hc/en-us/articles/26442819646999-Message-Bookmarks-and-Reminders). Its experiment/Nitro guidance predates the inspected build, so this implementation lets the server decide availability and quotas.

Rejected: local-only storage cannot sync with native Discord; UI/webpack automation depends on unstable private modules; a parallel gateway or direct Node HTTP path would bypass the existing request protections. A second host scheduler could duplicate native reminders and is excluded.

## Validation

Contract tests cover exact native request shapes, both list formats, pagination cursor progress, malformed responses, missing messages, server limit refusal, invalid paths/IDs/source/time, account switches before queued sends and after responses, posting relock during retries, privacy filtering (including hidden references in unarchived summaries), and local calendar/DST behavior. Renderer tests exercise stale response rejection and pagination fencing. Run typecheck, focused tests, full tests and build. Two separate Opus agents adversarially review transport/privacy and state/UI/concurrency; verified findings are fixed and regression-tested before completion.

Final validation on October 11: typecheck and production build passed; full suite 285 files, 2,189 passed and 7 skipped. The four focused saved-message files passed 49 tests, and the private Discord plugin check passed all five stages (36 tests). Both independent Opus reviewers returned APPROVE after findings were corrected. Browser QA used actual Solid components with synthetic data: past times rejected before a write, bookmark/reminder conversion, dialog reopening, posting-lock closure, privacy clearing, failure retention with disabled actions, new-session adoption and a 360px viewport without horizontal overflow.

Non-blocking review residuals: a late-started view whose first read overlaps a new session event may require another explicit Refresh; core-only permission changes without a gateway event may leave a menu offer stale, but every write rechecks current permission. Assumption: native gateway member/guild arrays contain ordinary non-null entries; malformed entries currently fail closed. A crafted unarchived bare identity cannot prove a channel and is treated as a new save requiring current access. These do not grant posting, privacy or account bypasses.

Live read QA on October 10 returned Discord 404 “Unknown Saved Messages.” This is handled as an account availability refusal with explicit retry; no entitlement, experiment, endpoint fallback or alternative transport is used. Positive live save/complete and notification QA remain unavailable for that account.

Preserving these invariants is verifiable in code and tests. It does not establish that Discord cannot identify ChattyPop.
